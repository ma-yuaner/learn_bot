# 开源项目与工具实战路线

这条路线不替代 Python、算法、数据库、Web API、部署和安全基础，而是在具备前置能力后，用真实项目检验工具选择、需求澄清和架构判断。候选名称来自学习者提供的清单；正式纳入课程前必须核对官方仓库、许可证、维护状态、数据权限和可复现实验，当前文档不表示这些工具已经安装或获得安全认可。

## 主综合项目：SlopWatch

SlopWatch 是一个计划中的自托管编程 Agent 监控平台，用来追踪团队使用 Claude Code、Codex 等编程 Agent 时的 token 消耗、会话质量和 context window 占用。

### 为什么放在后期

该项目会同时使用：

- Python 或其他后端语言的工程化能力。
- Postgres 数据建模、索引、事务和聚合。
- HTTP API、认证、部署和可观测性。
- Agent 事件格式、适配器、版本兼容和隐私脱敏。
- DDD 的统一语言、边界、聚合和架构决策记录。

因此合理顺序是：算法学习期间先保存项目问题；完成数据库、API、安全和部署区域后再进入完整实现。

### 用户提供的基线决策

- 产品形态：自托管，不做 SaaS。
- 初始部署：单二进制应用 + Postgres。
- v1 认证：管理员签发 token。
- v2 认证：OIDC。
- 初始统一语言：`session`、`turn`、`model request`、`listener`、`server`、`DAG`、`sidecar`。
- 候选接入对象：Claude Code、Codex、Crush、OpenCode、Copilot CLI。

这些是待验证的设计输入，不是不可修改的事实。每项都必须配套“为什么现在这样选、什么证据会触发改变”。

### 分阶段关卡

#### SW00 · GrillMe 需求诘问

不写业务代码，连续追问并留下决策证据：

- 谁是第一批用户：个人开发者、团队管理员还是平台工程师？
- 监控数据属于开发者、团队还是公司？
- token、提示词、工具调用和代码片段分别保存到什么粒度？
- “会话质量”是人工评分、规则指标还是模型评估？
- 不支持哪些场景，v1 明确不做什么？

产出：问题清单、答案、未决项、非目标和风险登记表。

#### SW01 · DomainModel 与统一语言

为每个术语写定义、身份、生命周期和不变量，禁止同一个词在不同模块表达不同含义。

初始关系假设：

```text
Session
└── Turn
    ├── ModelRequest
    └── ToolActivity

Listener/Sidecar → Ingestion → Server → Postgres → Metrics/Review
```

需要验证：

- 一个 turn 能否包含多个 model request？
- DAG 表示 Agent 执行关系，还是数据处理依赖？
- listener 与 sidecar 是部署角色、领域对象还是适配器名称？
- 会话跨进程恢复时，身份如何保持稳定？

产出：上下文图、术语表、聚合边界、事件表和至少五条不变量。

#### SW02 · 接入协议研究

针对每种 Agent 建立独立证据表：

- 官方 hook、事件或 JSONL 是否存在。
- 字段、顺序、版本和缺失数据。
- 是否能获取 token、context、模型、工具调用和错误。
- 数据读取权限、隐私风险和失败模式。
- listener 是文件跟踪、hook、代理还是 sidecar。

禁止用一个 Agent 的格式直接代表其他 Agent；共同模型由适配器映射得到。

#### SW03 · 最小纵向切片

选择一个 Agent，只实现：

```text
原始事件 → 解析 → 统一事件 → Session/Turn 聚合 → Postgres → 一个查询页面
```

验收包括重复事件幂等、乱序、进程重启、损坏记录、超大记录和版本不兼容。

#### SW04 · 指标与质量

- token 输入、输出、缓存和总量口径。
- context window 当前占用、峰值和接近上限事件。
- session、turn、model request 三个层级的成本聚合。
- 会话质量的人工证据、自动指标与模型评估分开保存。
- 指标版本化，避免公式变化后历史数据无法解释。

#### SW05 · 自托管、安全与认证

- 单二进制配置、迁移、备份、恢复和健康检查。
- 管理员 token 的生成、哈希存储、吊销、轮换和审计。
- 敏感提示词、代码路径和工具参数的脱敏策略。
- OIDC 进入 v2 前先定义租户、用户、角色和数据所有权。

#### SW06 · 多 Agent 与开源发布

- 每个 Agent 使用独立 adapter 契约测试。
- 发布兼容矩阵，不声称未经测试的支持。
- 提供最小部署、示例数据、架构决策记录和贡献指南。
- 明确许可证、遥测默认值、安全报告和数据删除方式。

### SlopWatch 考核

- 能用统一语言讲清从原始事件到指标的完整数据流。
- 能解释单二进制 + Postgres 适合哪个阶段，以及何时需要拆分。
- 能处理幂等、乱序、部分失败、格式升级和敏感数据。
- 能比较 hook、文件 listener、sidecar 和代理接入的取舍。
- 能根据三人团队、增长期团队和平台团队给出不同部署与治理方案。
- 能在面试官追问下修改设计，而不是维护最初答案。

## 开源工具实战支线

### 建模与需求

- `drawio-skill`：把领域关系、数据流和部署边界转成可版本化图示。
- `GrillMe`：练习在实现前发现模糊目标、隐含约束和冲突答案。
- `DomainModel`：建立统一语言、实体、值对象、聚合和上下文边界。

### Skill 发现与构建

- `skill-creator`、`find-skills`：学习能力发现、指令边界、输入输出契约和维护。
- `office-hours`、`superpower`：作为候选工作流案例，重点评估它们解决的问题和引入的流程成本。

### 研究、浏览器与知识整理

- `agentreach`、`notebooklm skill`、`bb-browser`、`playwright mcp`：用于资料收集、浏览器自动化和端到端验证候选实验。

### 前端与表达

- `frontend-design`（学习者清单中写作 `frontend-desion`，落地前核对准确项目名）。
- `ui-ux-pro-max`：用于界面信息层级和交互评审候选实验。
- `humanizer-zh`：用于中文表达修订候选实验，但必须保留技术事实和来源，不能用润色掩盖错误。

## 每个工具的统一验收模板

1. 找到并记录官方仓库与版本，不依据二手名字直接安装。
2. 检查许可证、更新频率、维护者、已知安全问题和依赖权限。
3. 用同一项小任务建立“不使用工具”的基线。
4. 使用工具完成任务，记录时间、修改次数、失败和人工修正。
5. 比较质量、效率、可解释性、隐私和供应链风险。
6. 写出适用场景、不适用场景、替代方案和卸载/回滚方式。
7. 只有证据显示净收益时，才进入主项目默认工具链。
