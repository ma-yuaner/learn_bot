# 通用项目展示框架架构

## 目标

同一个框架可以展示不同项目，而不需要复制并重写页面逻辑。具体项目只负责提供内容，框架负责校验、渲染、交互和本地状态。

```text
project.config.js        data/modules.js
       │                       │
       └──────────┬────────────┘
                  ▼
             lib/schema.js
                  │
                  ▼
               app.js
       ┌──────────┼──────────┐
       ▼          ▼          ▼
  页面渲染    场景交互    学习/证据状态
```

## 边界

- 品牌层：标题、摘要、版本、状态、主题与指标。
- 内容层：问题、结果、架构节点/边、决策、流程、交互、测验和交付物。
- 协议层：验证必填字段、唯一 ID、合法状态、架构引用和测验答案。
- 展示层：响应式页面和模块切换，不包含具体项目文案。
- 状态层：以项目 ID + 版本隔离本地测验与交付证据。

## 为什么使用配置而不是页面复制

- 修改项目内容不会碰框架核心。
- 每个模块都遵循相同的讲解与验收结构。
- 内容错误可以在 CI 中提前发现。
- 同一套视觉和交互可以稳定复用。
- 需要新能力时扩展协议一次，所有项目都能使用。

## 扩展原则

简单场景使用 `interaction.controls + outcomes` 配置，不执行任意字符串代码。如果某类项目需要图编辑器、代码运行器、时间序列图或真实 API，应把它实现成具名、可测试的交互插件，再由模块声明插件类型。不要在内容文件中使用 `eval`。

## 创建流程

```bash
npm run create:showcase -- ./target-directory "Project Name"
```

脚手架只创建不存在的新目录，拒绝覆盖已有目标。创建后：

1. 修改 `project.config.js`。
2. 用真实模块替换 `data/modules.js` 示例。
3. 运行 `npm run check` 和 `npm test`。
4. 根据项目需要增加部署配置。

## 适合的项目

- SlopWatch 等开源项目架构与迭代记录。
- AI Agent、RAG、模型评估和数据平台项目。
- Web 服务、内部工具、自动化系统和作品集。
- 课程模块、技术方案评审和面试项目讲解。

不适合把大量实时业务逻辑直接塞入配置文件；框架用于展示、推演和验收，真实业务系统仍应保持自己的领域与部署边界。
